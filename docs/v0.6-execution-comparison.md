## 3. BuyIntent 字段差异

`decision::build_intents` 产生的 BuyIntent 是 cleanup 唯一改的地方。

### 3.1 `reason`

| Main 可能值 | Cleanup 可能值 |
|---|---|
| `Chase` (FV gap ≥ 10c) | — |
| `Rebalance` (偏仓配平) | — |
| `JumpChase` (binance ±$30 jump) | `JumpChase` (binance ±**$15** jump) |

> Main 三路径都可能产生 BuyIntent；Cleanup 只生成 `JumpChase`。

### 3.2 `target` 和 `worst`

| 触发 reason | Main target | Main worst | Cleanup |
|---|---|---|---|
| **Chase** | `fv.fair_up − 0.06`（safety_margin） | `target + 0.02`（chase_worst_slippage，走簿 2c） | 不产生 |
| **Rebalance** | `fv.fair_up − 0.06` | `(1.0 − avg_opposite) − 0.02`（merge 分水岭） | 不产生 |
| **JumpChase** | `fv.fair_up − 0.06` | `target + 0.04`（jump_worst_slippage，走簿 4c） | **`up_ask`（target = worst = best_ask，只吃一档）** |

> 核心差异：cleanup 把 worst 钉死在 best_ask，**禁止走簿吃深档**。
> 实证理由：薄盘 walk 多档会把 VWAP 推到 0.55-0.65，吞掉 1-2c spread alpha。

### 3.3 `qty`

| 触发 reason | Main qty | Cleanup qty |
|---|---|---|
| Chase | `MAKER_BUY_CHASE_MIN_QTY = 30 张` | 不产生 |
| Rebalance | `(opposite_qty - my_qty).max(MIN_ORDER_QTY=5)` 动态 | 不产生 |
| JumpChase | `JUMP_CHASE_QTY = 5 张` | `JUMP_CHASE_QTY = 15 张` |

> Cleanup jump qty 从 5 → 15，因为路径不再"小仓试探兜底"，而是**唯一 alpha 入口**。

## 6. 一个待解的现象 ⚠️

### 观察：Main 时代连续 5 笔同方向 UP buy

```
窗口 1779441900 (09:20-09:25 UTC):
  09:21:07.941  UP buy 15 张 @ 0.37
  09:21:08.966  UP buy 1.75 张 @ 0.53  (partial fill)
  09:21:10.372  UP buy 15 张 @ 0.56
  09:21:11.406  UP buy 15 张 @ 0.58
  09:21:12.510  UP buy 15 张 @ 0.58
```

5 笔同侧买入，间隔约 1 秒。**力度上**：

- 这违反 force-balance（qty_up=15 后再买 UP 应被 `qty_up ≤ qty_down` 拦住）
- 同窗口 trades CSV 没看到对应 DOWN 成交

### 可能解释（**未验证**）

A. **rebal 在 UP 之间下了 DOWN 配平，且立即 merge**
   - 但 merge 不写 trade row，DOWN 成交应该出现在 trades CSV
   - 而 CSV 只显示 5 UP（无 DOWN）—— 跟假设矛盾

B. **trades CSV flush 时机问题**
   - 主版可能在 reset_for_new_window 之前 flush，部分 DOWN 成交被划入下一窗口
   - 窗口 1779442200 的 CSV 是空的（只 header），跟此假设不一致

C. **Main 版 force-balance 守门有隐性绕过逻辑**
   - chase / rebal / jump 三路径之间的相互优先级可能有 race
   - 例如 jump_buy_up 检查 `!chase_buy_up`，而 chase_buy_up 检查 `up_chase = ... && fv_up_rising`
   - FV-rising 在 5s 内可能反复 true/false → balance check 跨决策窗口可能错位

D. **Trades CSV 单元是 fill，不是 order**
   - 一个 IOC 走 5 档可能产生 5 个 trade rows
   - 但 ioc.rs 实现里所有 fill 共享同一个 ts_ms 参数
   - 而这 5 笔 ts_ms 间隔 1 秒，不像同一 IOC 的 5 个 fill

**结论**：力度上需要单独建 task 复盘 main 版的 force-balance 与多触发路径的交互。
当前 cleanup 已经把 force-balance 守门加回（commit 59c3686），单一路径无优先级 race，**这个现象在 cleanup 下不会出现**。
